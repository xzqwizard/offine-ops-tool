## 3. 具体发现

### R01 [P1] 增量升级包必经的模板没有注册

位置：[builder.rs:53](D:/OffinePreOpsTool/src-tauri/src/builder.rs:53)、[builder.rs:1153](D:/OffinePreOpsTool/src-tauri/src/builder.rs:1153)。

`build_server` 在升级模式调用 `render("scripts/upgrade.sh.j2")`，但 `TEMPLATES` 中没有该模板，`template_env()` 也没有其他注册入口。选择合法基线后仍会在渲染阶段失败。现有“所有模板可渲染”测试只遍历注册表，所以无法发现注册表漏项。

建议：补齐模板注册，并通过真实升级构建入口验证完整产物清单。**隔离复现确认。**

### R02 [P1] Docker 官方静态包在线下载无法正常入库

位置：[docker_pkgs.rs:345](D:/OffinePreOpsTool/src-tauri/src/docker_pkgs.rs:345)、[docker_pkgs.rs:72](D:/OffinePreOpsTool/src-tauri/src/docker_pkgs.rs:72)。

下载文件名是 `docker-<arch>-<version>-<时间>.tgz.downloading`，随后原样交给导入器。导入器只接受以 `.tgz` 结尾且版本部分只有数字/点的名字，因此该临时文件被跳过。接着读取预期包组的 `meta.json`，在没有旧包时失败；已有旧包时可能返回旧材料，看似下载成功。

建议：下载校验后以标准名称入库，或直接用已知 arch/version 写包组，不从临时文件名反推。检查导入结果中是否确实创建了目标包组。**隔离复现确认。**

### R03 [P1] 镜像库页面拉取传入 ComputedRef，IPC 序列化失败

位置：[ImagesView.vue:131](D:/OffinePreOpsTool/src/views/ImagesView.vue:131)、[backend.ts:148](D:/OffinePreOpsTool/src/api/backend.ts:148)。

调用传入的是 `projectRegistry`，没有取 `.value`。这是含循环引用的 Vue 计算属性对象，序列化时抛错；即使某条传输路径没有循环错误，后端也需要 `RegistryConfig`，无法接受 Ref 结构。接口使用 `unknown`，类型检查没有阻止该错误。

建议：传递 `projectRegistry.value`，并将所有 registry 参数声明为 `RegistryConfig | null`，自定义模板参数也使用明确类型。**当前 Vue 对象序列化复现确认。**

### R04 [P1] 工具数据恢复缺少子目录、设置与数据落位不一致

位置：[commands.rs:200](D:/OffinePreOpsTool/src-tauri/src/commands.rs:200)、[SettingsView.vue:279](D:/OffinePreOpsTool/src/views/SettingsView.vue:279)。

ZIP 条目 `projects/proj-xxx/project.json` 只创建 projects 根目录，没有创建 `proj-xxx`，恢复到新机器或恢复已删除方案时必然失败。父目录缺失已用同样的文件写入路径复现。

此外，恢复前按当前设置固定 `projects_root`，过程中却覆盖备份内的 `settings.json`。备份和当前 projectsRoot 不一致时，方案写入 A，恢复后的应用却从 B 读取。逐文件覆盖也没有预验证/事务：失败时可能已改设置及部分方案。前端成功后只清空方案 store，设置表单仍保留旧值，再点保存会覆盖恢复的设置；恢复前也没有等待所有在途保存结束。

建议：先解压到临时目录，验证 JSON、结构和路径，再确定目标存储策略；逐文件建立真实父目录；备份旧数据并原子提交；恢复前停止/等待写任务，恢复后重新加载设置。**目录缺失复现确认，其余静态确认。**

### R05 [P1] 中文长名称导致 panic，名称净化碰撞会覆盖服务器包

位置：[builder.rs:184](D:/OffinePreOpsTool/src-tauri/src/builder.rs:184)、[builder.rs:787](D:/OffinePreOpsTool/src-tauri/src/builder.rs:787)。

`String::truncate(64)` 按字节截断，64 可能落在中文 UTF-8 字符中间。22 个连续中文字符即能触发 panic。发布配置是 `panic = "abort"`，可能直接退出应用，而不是正常返回构建错误。

另外，`app/01` 与 `app?01` 都净化为 `app-01`；同架构服务器最终目录/包名相同，后一个包覆盖前一个。前端只检查原始名称唯一，不能避免净化后碰撞；长名称截断、Windows 大小写也存在类似风险。

建议：按字符边界截断；产物路径使用稳定 serverId 或追加其摘要；创建产物前检测所有路径唯一性。**两种场景均隔离复现确认。**

### R06 [P1] 渲染字段校验没有阻止 shell 命令替换

位置：[builder.rs:306](D:/OffinePreOpsTool/src-tauri/src/builder.rs:306)、[deploy.sh.j2:41](D:/OffinePreOpsTool/engine-templates/scripts/deploy.sh.j2:41)。

服务器名称、部署路径等只禁止换行/双引号/反引号，没有禁止 `$()`、`${}` 和其他 shell 解释。方案名称、OS/版本、网络协议、参数键及远程模板字段也未得到完整的上下文校验。字段原样嵌入双引号、单引号或 shell 代码，合法通过工具校验的名称 `$(printf REVIEW_ONLY)` 会保留为命令替换表达式；现场 root 执行脚本时会解释它。此处仅验证了校验放行，没有执行注入表达式。

建议：不同输出上下文分别编码，shell 数据用可靠引用、JSON/YAML 用序列化器；协议/IP/路径/环境变量键按语义校验；远程目录中的可执行字段明确设置信任边界。**校验放行隔离复现确认，模板插值静态确认。**

### R07 [P1] 缺失或错误镜像仅告警，仍生成“成功”离线包

位置：[builder.rs:1061](D:/OffinePreOpsTool/src-tauri/src/builder.rs:1061)、[builder.rs:1108](D:/OffinePreOpsTool/src-tauri/src/builder.rs:1108)。

本地 tar 不存在、在线拉取失败、缓存未命中都会加入 warnings 后继续；tar 无 manifest、标签不匹配同样只是告警。包内 Compose 仍保留该服务，构建报告和历史可以将它视为成功完整包，CLI 也返回 0。完全离线目标机无法补拉这些镜像。

建议：默认自包含构建必须逐实例验证镜像存在、格式、标签/平台。若支持“目标机已有镜像”，将其做成明确的外部前提模式，并在现场先验证。缺材料的构建不能作为正常成功基线。**静态确认。**

### R08 [P1] digest 只是记录值，没有锁定实际镜像或验证一致性

位置：[builder.rs:146](D:/OffinePreOpsTool/src-tauri/src/builder.rs:146)、[builder.rs:1083](D:/OffinePreOpsTool/src-tauri/src/builder.rs:1083)、[InstanceFormDialog.vue:403](D:/OffinePreOpsTool/src/components/project/InstanceFormDialog.vue:403)。

拉取和缓存按 `inst.image` 执行，没有把独立的 `inst.digest` 纳入拉取约束或核验；清单却优先记录该字段。tag 指向改变后，实际 tar 与报告中的 digest 可能不同。编辑镜像引用但不重新检查时又会保留旧 digest。升级比较会把这种旧记录当成一致依据，从而错误跳过镜像。

同 tag 的本地 tar 被替换时，若基线没有 digest，升级逻辑仅凭裸引用跳过，没有比较 tar 内容。本地 tar 已锁 digest 时，比较阶段还探测缓存的 meta，未核验本地文件。

建议：区分期望 digest、实际拉取 digest、tar SHA256；按期望 digest 拉取并核验；改引用清除旧锁定值；本地 tar 的变更比较使用可验证的内容标识。**静态确认。**

### R09 [P1] 镜像缓存键可以碰撞，且没有隔离项目私有源

位置：[images.rs:411](D:/OffinePreOpsTool/src-tauri/src/images.rs:411)、[images.rs:532](D:/OffinePreOpsTool/src-tauri/src/images.rs:532)、[builder.rs:1076](D:/OffinePreOpsTool/src-tauri/src/builder.rs:1076)。

repo 内 `/` 直接替换为 `_`，例如 `team/app:1` 与 `team_app:1` 会得到同一缓存文件名。不同镜像可能复用错误 tar。

同时，项目 A/B 各自配置不同私有仓库，但实例都写同一个 Docker Hub 逻辑引用时，缓存仍只按逻辑引用+平台定位。A 拉取私有仓库内容后，B 会直接命中 A 的文件，完全绕过 B 的私有仓库。修改同一方案的私有仓库也有这个问题。

建议：使用结构化完整键的哈希，纳入实际来源/锁定 digest/平台；命中时核对 meta；原始名称只用于展示。**静态确认。**

### R10 [P1] MinIO 预置配置缺少运行服务的 command

位置：[preset.json:89](D:/OffinePreOpsTool/catalog/preset.json:89)、[docker-compose.yml.j2:20](D:/OffinePreOpsTool/engine-templates/compose/docker-compose.yml.j2:20)。

MinIO 条目只有镜像、环境变量、卷和端口，没有 `server /data --console-address :9001`。Builder 仅在目录提供 command 时输出覆盖命令，工具不能生成其标准服务启动参数，也不能保证控制台固定监听已声明的 9001。两个架构快捷模板都包含 MinIO，因此会影响常用方案。

建议：补齐启动命令，按指定镜像版本做 API/console 启动和数据重启持久化验收。**配置缺项静态确认，指定远程镜像的运行结果尚未实测。**

### R11 [P1] 升级、回滚不能保证回到原来的可用状态

位置：[upgrade.sh.j2:35](D:/OffinePreOpsTool/engine-templates/scripts/upgrade.sh.j2:35)、[upgrade.sh.j2:91](D:/OffinePreOpsTool/engine-templates/scripts/upgrade.sh.j2:91)、[upgrade.sh.j2:133](D:/OffinePreOpsTool/engine-templates/scripts/upgrade.sh.j2:133)。

以下问题在补齐 R01 后仍存在：

- 从升级包自己的目录运行，会首先把升级包内 `stack/docker-compose.yml` 当成原部署目录，数据卷指向空目录。脚本没有排除 PKG_DIR。
- 只验证目录有 Compose，没有验证当前 project/server/buildId 与声明基线对应，可能升级错环境。
- 先覆盖原 Compose 再 `config`、`up`；这两步失败会因 `set -e` 直接退出，没有恢复动作，也走不到健康失败的 U3 提示。

- `--dry-run` 仍检查真实容器健康，可能超时或以旧容器状态误判升级完成；运维脚本在健康检查前已覆盖。

建议：明确现场身份与版本、验证新配置后再提交；保留旧 imageId/digest 与数据备份；对失败阶段设置恢复动作；定义删除服务、新增卷权限和数据迁移策略。**静态确认。**

### R12 [P1] 数据库备份和恢复不形成可靠闭环

位置：[builder.rs:989](D:/OffinePreOpsTool/src-tauri/src/builder.rs:989)、[ops.sh.j2:109](D:/OffinePreOpsTool/engine-templates/scripts/ops.sh.j2:109)、[OPS-GUIDE.md.j2:62](D:/OffinePreOpsTool/engine-templates/docs/OPS-GUIDE.md.j2:62)。

逻辑导出失败只提示“依赖文件级快照”，但文件级 tar 在数据库运行时执行，没有停库/一致性快照。即便 tar 成功，也不代表可以恢复。手册最终又统一引导解压 tar 恢复，没有对应 SQL、Mongo archive、Redis RDB 的可验证恢复流程。

PostgreSQL 导出固定 `-U postgres`，与可配置的 `POSTGRES_USER` 不一致；启用鉴权的 Mongo 导出没有账号密码/authenticationDatabase；Redis 的 BGSAVE 固定等待 2 秒，不能保证完成，可能复制旧 RDB。MySQL `--single-transaction` 也不能泛化为所有引擎/DDL 场景的一致性保障。

多个方案在同一 deployBaseDir 下共用 `backup/`，每个脚本都清理整个目录到 5 份，存在跨方案删除备份和同秒目录碰撞。

建议：定义每种数据库的在线一致性备份和恢复契约；失败返回明确状态，不把活库 tar 当可靠替代；备份路径按项目/服务器隔离，只对成功完整备份实施保留策略；用恢复演练验收。**静态确认，未做真实数据库备份/恢复。**

### R13 [P1] 防火墙脚本不能兑现 Docker 发布端口的来源白名单

位置：[apply-firewall.sh.j2:19](D:/OffinePreOpsTool/engine-templates/scripts/apply-firewall.sh.j2:19)、[apply-firewall.sh.j2:26](D:/OffinePreOpsTool/engine-templates/scripts/apply-firewall.sh.j2:26)、[docker-compose.yml.j2:18](D:/OffinePreOpsTool/engine-templates/compose/docker-compose.yml.j2:18)。

Compose 将端口发布到所有接口；iptables 分支只写 INPUT ACCEPT，既没有匹配 Docker DNAT 后的 FORWARD/DOCKER-USER 流量，也没有形成拒绝未授权来源的策略。firewalld rich-rule 同样不能脱离 Docker 的转发规则假定访问限制已经成立。

此外，`firewall-cmd ... && echo ...` / `iptables ... && echo ...` 没有显式累计失败，前面的失败有机会被后续成功和“完成”掩盖。

建议：明确该脚本是“开通辅助”还是“访问隔离策略”；后者需针对目标 Docker 防火墙后端设计并验证实际流量，分别从允许/禁止 IP 进行连接验收。**规则链缺口静态确认，具体 OS/Docker 的网络行为需实机验证。**

### R14 [P1] UDP 配置在 Compose 中被生成成 TCP，矩阵还可能写错协议

## 4. 预置中间件还需要专项验收

R10 已单独列出 MinIO 的启动缺项。其余条目不宜仅凭 Docker 容器 Running 或命令退出 0 判定业务可用：

| 条目 | 应补的验收 |
|---|---|
| MySQL | 必填/可选账号参数成组校验，正确/错误密码连接，重启持久化，dump 恢复 |
| Redis | 密码启用后健康检查带鉴权并检查 PONG，等待 RDB 保存完成后核对时间；不能只依赖 redis-cli 进程退出码 |
| PostgreSQL | 自定义 POSTGRES_USER 的建库、健康检查、导出和恢复保持一致 |
| MongoDB | root 用户名与密码成组，鉴权后的导出/恢复；官方 mongo 镜像是否具备 mongodump 需按版本验证 |
| Nginx | 空宿主卷覆盖默认 html 后的 403；curl 缺 `-f` 会将 HTTP 4xx/5xx 当成功；默认 HTTPS 443 没有证书配置，声明端口不能等同于实际提供 TLS |
| MinIO | server command、固定 console 地址、API/console 可用及数据重启持久化 |
| RabbitMQ | 默认账号/密码配置、跨机连接及数据目录恢复 |
| Kafka | 指定 Bitnami tag 当前是否可拉取，controller listener 名与协议映射、advertised 地址；默认字段需要用真实 KRaft 启动验证 |
| Elasticsearch | vm.max_map_count 不满足时只 warn，应用仍可能启动失败；HTTP 检查需判断状态码和集群状态 |
| Nacos | 指定版本镜像架构、HTTP readiness、9848 及自定义映射时的 gRPC 端口关系 |

镜像 tag 当前是否仍公开存在、镜像内是否包含特定工具、国产 OS 与内核兼容性，本轮没有通过真实拉取/真机验证，不能当成已经确认通过的事项。

## 5. 优化建议与实施顺序

### 第一批：修复可以直接复现的主路径失败

处理 R01/R02/R03/R04/R05/R10/R14/R16：升级模板、下载入库、IPC 类型、ZIP 恢复、名称处理、MinIO 启动、协议生成、插件补齐。新增测试应走真实业务入口，防止仅测试内部注册表/字符串存在而遗漏功能连线。

### 第三批：补齐现场运维和异常恢复

### 第四批：任务和交互一致性

## 6. 建议的验收清单

1. 快捷模板、复制、导入的方案补齐信息后通过同一后端校验；缺 IP/端口冲突/不存在架构/材料缺失能够被准确阻断。

4. 首次部署全部声明服务与端口可用；已有 Docker 缺 Compose 可补齐；端口改映射与 UDP 可用；重跑部署不会误阻断自己的容器。
5. 同一服务器连续升级两次，配置失败/启动失败/健康失败均有可执行恢复路径；同 tag 更新、新增非 root 服务、删除服务均覆盖。

7. 工具 ZIP 在全新环境以及不同自定义存储路径下恢复成功，自定义模板保留；损坏 ZIP 不破坏当前数据。
8. 快速切方案、预检时切方案、构建时离开页面、关窗和写入失败不会串方案或丢编辑；后台任务可准确追踪。
9. 已授权 IP 可以访问、未授权 IP 不能访问，规则执行失败有明确失败结果；覆盖目标机实际 Docker/firewall 后端。
