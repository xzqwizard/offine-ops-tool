## 2. 业务闭环判断

| 业务链路 | 当前判断 | 主要缺口 |
|---|---|---|
| 新建/复制/导入 → 编辑 → 保存 → 重新加载 | 基本具备 | 关联端口编辑后无法直接保存；失败编辑留在内存；特殊凭据前缀影响重载 |
| 目录选择/自定义 → 健康检查 → 可用性判定 | 部分闭环 | 自定义目录条目自动生成 `true` 探针，不能证明业务就绪 |
| 在线拉取/缓存/本地 tar → 完整镜像交付 | 部分闭环 | 相同 tag 的不同内容会合并为同一运行身份；本地 tar 与隐藏 digest 锁冲突 |
| Docker/Compose 材料 → 全量交付 → 安装 | 部分闭环 | 校验清单与复制清单不同；插件入库后缺少完整校验；目标检查晚于系统修改 |
| 全量部署 → 同版本重跑 → 巡检 | nginx/PostgreSQL 的当前 CI 场景已执行 | 新安装 Docker、其它中间件与其它 OS/CPU 组合仍需目标验收 |
| 来源规则 → 现场白名单 → 拒绝来源验证 | 未闭环 | 当前真实 CI 已失败 |
| 运行服务 → 冷备份 → 正确镜像/数据恢复 | 未充分闭环 | tag 漂移时备份镜像错配；当前真实 CI 的恢复验证未执行到 |
| 基线 → 增量升级 → 成功确认 | 部分闭环 | 数据路径/实例迁移没有策略；实际成功升级的数据验证未执行到 |
| 升级失败 → 自动回滚 → 正确失败状态 | 未闭环 | 回滚内部命令失败可被忽略，日志可误报恢复完成 |
| 工具数据 ZIP/方案导出 → 新环境恢复 | 本地回归通过 | 密码按设计需要重填；跨机器、磁盘故障和实际用户目录仍需演练 |
| 长任务 → 切页/关窗 → 结果及错误可追踪 | 构建任务已有机制 | 拉取、引擎和材料下载未统一纳入生命周期；子进程缺少应用级截止时间 |

“业务闭环”还应包含错误后有准确状态、能恢复到可核验版本，并确认数据与访问策略正确。服务 Running、健康命令退出 0、构建历史标记 complete，分别只能证明对应检查点。

## 3. 当前发现（按修复优先级）

### R01 [P1] 来源白名单在当前真实 Docker CI 中未拒绝禁止来源

位置：[apply-firewall.sh.j2:8](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/apply-firewall.sh.j2#L8)、[apply-firewall.sh.j2:22](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/apply-firewall.sh.j2#L22)、[acceptance-smoke.sh:36](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/scripts/acceptance-smoke.sh#L36)。

脚本仅在 IPv4 `DOCKER-USER` 转发链按原目标地址/端口限制来源。当前 CI 实际执行该脚本后，`.11` 拒绝来源仍能访问 nginx 发布端口，脚本“白名单已应用”的输出不能作为策略有效的凭据。此项已由真实 CI 确认，不需要用假设代替失败证据。

建议先保留失败现场的 Docker 版本、daemon 配置、iptables/nft 后端、规则及计数器、监听进程和连接原目标信息，定位实际流量路径；再明确并实现受支持路径的限制。补测宿主外部来源、桥接网络来源、允许/拒绝来源、TCP/UDP、重启持久化、升级后换端口，并让不受支持的配置明确失败。不能仅删除拒绝来源断言使 CI 变绿。

证据：真实 CI。具体绕过路径尚待定位。

### R02 [P1] 自动回滚的条件调用会使恢复函数忽略关键命令失败

位置：[upgrade.sh.j2:30](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/upgrade.sh.j2#L30)、[runtime.sh.j2:124](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L124)、[runtime.sh.j2:175](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L175)、[runtime.sh.j2:189](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L189)。

升级的 EXIT trap 用 `if ! restore_snapshot ...` 调用恢复函数。Bash 对作为条件判断执行的函数/复合命令会抑制 `errexit`；函数内部的 `set -e` 不能保证每条失败命令退出。恢复中的 `docker load`、`compose down/up`、`docker tag`、目录移动等多处只依赖 `set -e`。

隔离验证让恢复镜像的 `docker load` 固定返回 41：手工 `ops.sh restore` 返回 41，未打印恢复完成；通过候选升级失败进入自动回滚时，该错误被忽略，仍设置成功状态并记录恢复完成。最终升级进程返回的是候选失败码 17，没有返回“自动回滚失败”的 2。mock 后续健康检查能通过，所以当前额外状态检查不能兜底所有恢复错误。

建议所有改变镜像、服务、目录、身份和防火墙的恢复命令显式检查返回值，让恢复成功条件依赖全部阶段成功；避免用条件调用配合 `set -e` 作为唯一保障。加入恢复阶段 load/down/tag/mv/up/health/firewall 分别失败的测试，检查退出码、保留目录、镜像 ID 和数据状态。

证据：当前模板的故障注入复现；实际数据库恢复失败尚未在本机验证。

### R03 [P1] 同一 tag 的不同 digest/本地内容最终使用同一个运行标签

位置：[render_context.rs:90](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/render_context.rs#L90)、[images.rs:444](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/images.rs#L444)、[builder.rs:860](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/builder.rs#L860)、[builder.rs:875](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/builder.rs#L875)。

实例用独立 `digest` 字段锁定远端内容，但 Compose 根据 `inst.image` 生成标签；只有引用字符串本身含 `@digest` 才生成唯一的 `offline.local` 标签。两个实例均为 `demo:v1`、digest 分别为 A/B 时，校验允许它们存在，构建会区分两个归档，却将归档改写回同一个 `demo:v1`。

调用实际 Rust 函数得到：校验问题列表为空，锁定引用分别为 `demo@sha256:A/B`，两个 Compose 服务的 image 均为 `demo:v1`。Docker 标签是 daemon 内的共享映射，后加载的版本会覆盖同名标签；两个服务无法按各自锁定内容可靠启动。本地 tar 不同内容但相同 tag，以及多方案共用 daemon，都有同类冲突。

建议以不可变内容身份派生交付标签，统一归档重写、Compose、manifest 和基线映射；即便同 tag，不同内容也需不同运行引用。验证同服务器两个 digest 并存及不同方案先后部署，核对容器实际 `.Image`。此次没有用真实 Docker 启动该双版本场景。

证据：实际 Rust 校验/渲染输出，结合构建代码及 Docker 标签语义。

### R04 [P1] 冷备份保存 tag 当前指向的镜像，可能不是运行容器的镜像

位置：[runtime.sh.j2:85](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L85)、[runtime.sh.j2:88](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L88)、[runtime.sh.j2:101](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L101)。

备份通过 `compose config --images` 获取引用，再 `docker image inspect "$ref"` 解析镜像 ID。另一套方案或手工 load 将同名 tag 从 A 改为 B 时，已有容器仍可继续运行 A。此时备份保存 B，恢复重新建容器后会运行 B，与备份时的数据/二进制组合不一致。

隔离场景模拟“运行容器 `.Image=A`，当前 tag `.Id=B`”：备份成功返回 0，`image-map.tsv` 和 `docker image save` 都选择 B，未查询容器 `.Image`。此问题即便没有 R03 中的双实例配置，也可以独立触发。

建议从每个实际部署容器提取不可变 `.Image`，保存服务、容器、镜像 ID 与交付引用的对应关系；对无容器的服务单独定义策略。若同一引用已对应多个运行版本，应先处理身份冲突。恢复后验证容器镜像 ID 与快照记录相符。

证据：当前模板的 tag 漂移模拟复现及代码链。

### R05 [P1] 实例改名/跨服务器移动没有数据迁移策略，升级可能启动空数据目录

位置：[compose.rs:10](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/compose.rs#L10)、[runtime.sh.j2:30](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/runtime.sh.j2#L30)、[MiddlewarePanel.vue:120](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src/components/project/MiddlewarePanel.vue#L120)、[baseline.rs:27](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/src-tauri/src/baseline.rs#L27)。

UI 可修改稳定实例 ID 对应的名称和目标服务器，持久化目录却由可编辑名称决定：`./data/{instance_name}`。保持同一实例 ID 把 `demo-one` 改为 `renamed` 后，实际 Compose 挂载从 `./data/demo-one` 变成 `./data/renamed`；同一服务器信息下的升级基线检查仍返回成功。

升级会创建新目录并启动服务。数据库可能自动初始化新数据并通过健康检查，旧数据文件仍在旧目录，但新服务读不到，且成功健康检查不会触发回滚。服务器集合不变、原服务器仍有其它服务时，跨服务器移动也不会携带原数据。现有冷备可以提供恢复点，不能自动完成正向迁移。

建议数据路径绑定稳定实例/存储 ID；对既有部署的改名、移动、数据挂载目标变化生成明确变更计划，支持受控迁移或阻断增量升级。新增真实数据库数据写入 → 改名/移动 → 升级 → 数据核对用例。

证据：实际 Rust 挂载渲染和基线接受复现；数据初始化后健康通过属于依服务行为产生的风险。

### R06 [P1] 架构/资源预检晚于 Docker 安装，现场 OS 也未按方案核对

位置：[deploy.sh.j2:14](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/deploy.sh.j2#L14)、[precheck.sh.j2:6](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/scripts/precheck.sh.j2#L6)、[install-docker.sh.j2:39](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/install/install-docker.sh.j2#L39)、[install-docker.sh.j2:55](https://github.com/xzqwizard/offine-ops-tool/blob/0b4e99c5c37eb5012b8a2c6531311206d31cf384/engine-templates/install/install-docker.sh.j2#L55)。

`deploy.sh` 先运行安装器，再运行架构、资源等预检。未安装 Docker 的目标机上，静态安装会先把二进制复制到 `/usr/bin`、写 Docker systemd unit/daemon 配置并启动服务。CPU 架构错误时，安装器可能在这些修改后失败，甚至无法走到架构预检。内存、磁盘、内核参数不满足时也会在安装后被拒绝。

安装器读取 `/etc/os-release` 的 ID 只用于打印，没有核对方案要求的 OS/版本。构建侧对材料的 OS 声明匹配不能证明现场机器匹配。

建议分为安装前检查与安装后检查：修改宿主前核对 CPU、OS/版本、必要工具、可用磁盘和安装权限；Docker 安装/Compose 补齐后再检查 daemon、真实 data-root、端口和运行能力。错发包应在系统修改前明确失败。

证据：完整部署调用顺序及安装模板静态确认；未在错误架构真机执行破坏性验证。

### R07 [P2] 修改发布端口/协议/归属后，旧访问规则使保存失败且内存已被修改

## 4. 依赖审计与安全边界

`pnpm audit --prod --registry=https://registry.npmjs.org --json` 当前报告 1 条 high advisory：锁文件中的 `source-map-js@1.2.1`，路径 `vue → @vue/compiler-dom → @vue/compiler-core → source-map-js`。对应 [GHSA-68fv-2mgg-jv7q](https://github.com/advisories/GHSA-68fv-2mgg-jv7q) / CVE-2026-93749，修复版本为 1.2.2。

该公告涉及 indexed source map 的 section offset 导致同步事件循环阻塞。本项目生产前端预编译模板，本轮未找到接收不可信 source map 并运行此解析器的业务入口，因此不能仅根据包的 high 评级宣称桌面产品已存在可远程利用的高危漏洞。建议更新受影响传递依赖并重新审计、构建；Rust 依赖另补 RustSec 审计。该依赖公告未计入上述 15 个功能/代码问题。

DPAPI 及便携导出脱敏已实现；现场 Compose、冷备数据及镜像仍包含部署所需敏感信息，应按生成手册管理。本轮没有发现可确认的前端 XSS 入口；`tauri.conf.json` 的 CSP 关闭属于加固机会，可在核对现有样式/字体资源后收紧。应保留“签名未实现、启用被拒绝”的准确边界，产物 SHA256 校验不等同于签名或来源认证。

## 6. 修复顺序与补充验收

第一批优先处理 R01–R06，先恢复访问策略和异常恢复可信度。R03/R04 应统一设计不可变镜像身份；R05 应明确存储身份和迁移契约；R06 将目标检查移到修改宿主之前。修复后每个结论都应绑定当前容器镜像 ID、业务数据和实际访问结果。

第二批处理 R07–R13、R15，补齐正常编辑、本地材料、自定义探针、材料清单、插件完整性和凭据往返。第三批完成 R14 与任务/缓存/交互优化。依赖更新可独立进行，避免与业务修复混为一批。

建议至少补齐以下验收证据：

1. **防火墙**：真实外部/桥接来源分别允许与拒绝，TCP/UDP、多个方案、端口改映射、Docker 重启和持久化后重复验证；失败保留计数器及 daemon 信息。
2. **镜像身份**：同机两个相同 tag 不同 digest、本地 tar 不同内容、两个方案交错 load；逐容器核对 `.Image` 与 manifest。tag 被另一方案覆盖后备份再恢复，仍回到备份时版本。
3. **回滚故障矩阵**：候选 load/config/up/health/firewall 失败，以及恢复 load/down/tag/mv/up/health/firewall 各阶段失败；检查返回码、目录保留、镜像和业务数据。模拟测试先补，再用真实 Docker 抽验。
4. **数据迁移**：实例改名、移动服务器、删除/新增持久化实例、模板挂载目标和数据库主版本变化，均有明确允许/阻断/迁移行为；读取真实业务数据验证，不能只检查进程就绪。
5. **首次安装**：全新目标机器、已有 Docker 缺 Compose、错误 CPU/OS/版本、内存/空间不足；错误包不应在阻断前修改系统。实际 RPM/DEB 依赖和静态 Docker/systemd 支持按目标发行版验收。
6. **材料门禁**：额外未声明文件、文件/meta 落盘失败、损坏缓存、20 字节插件、插件正文被破坏、离线锁定缓存、本地 tar 切换和私有仓库认证失败；只有确认的材料进入完整包。
7. **UI 与持久化**：端口/协议/服务器编辑连同规则保存，失败可撤回；快速切架构/方案、重复提交、任务中切页/关窗、超时取消及 `dpapi:` 原始密码往返；在 Tauri 桌面环境核对实际行为。
8. **中间件专项**：PostgreSQL 先让当前真实 CI 跑到冷备/恢复/升级/回滚后的 SQL 数据核对；MySQL、Redis、MongoDB、RabbitMQ、Kafka、Elasticsearch、Nacos、MinIO 再按鉴权、启动依赖、端口、持久化和恢复逐项验收。国产 OS/CPU、实际客户镜像和生产防火墙需对应环境证据。

已有 Linux CI 在一个前置防火墙断言失败后，后面的运维验证全部跳过。建议将网络与数据库恢复场景拆成各自有清理和诊断输出的测试单元，使一个场景失败时仍能取得其余链路的结果；交付要求的所有场景仍须分别通过。当前的脚本 mock 测试主要让候选版本失败，尚未证明恢复内部失败都能准确报告。

隔离复现包括 CI 失败日志、依赖审计、Rust 函数结果和脚本故障输出，关键结论已记录在本报告。后续修复与验收见下节。
