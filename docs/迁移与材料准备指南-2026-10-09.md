# 迁移与材料准备指南

适用本次修复后的版本。新增门禁会拒绝旧版没有可信元数据的 Compose 材料，以及没有稳定存储契约的升级基线；拒绝是为了避免错装插件或启动空数据目录。

## 旧部署转为稳定实例目录

新版数据目录为 `stack/data/<实例ID>/`，镜像运行引用为 `offline.local/image:<config SHA256>`。旧目录可能是 `stack/data/<服务名>/`。不要直接替换 Compose 后启动，也不要将旧 manifest 的版本字段手工改成新版本来绕过基线检查。

1. 保留原方案 ID、服务器 ID 和每个实例 ID，记录实际运行镜像 `docker inspect --format '{{.Image}}' <容器>`、镜像版本和 `docker inspect --format '{{json .Mounts}}' <容器>`。按“服务名 → 实例 ID → 实际源目录 → 容器挂载目标”制作映射；应以实际挂载为准。
2. 停止业务写入，使用旧版本可用的冷备或经业务确认的数据库备份，并验证可恢复。记录 SQL/文件数量及关键业务值，保留原包、编排、身份和镜像。停止本方案服务，不停止宿主 Docker 或其它方案。
3. 用本次版本为原方案生成新的全量包，先保持原镜像版本及数据挂载目标。确认新 `manifest.json` 中各实例的 `instanceId/serverId/dataDir/dataVolume/runtimeReference` 与映射一致。解压到独立部署目录；旧目录继续保留。
4. 在服务停止期间，把各持久化源目录完整复制到新包 `stack/data/<实例ID>/`，保留数字 UID/GID、权限和业务要求的文件属性。若源含符号链接、外置目录或其它特殊文件，按数据库/中间件专用迁移方案处理，不依赖通用冷备脚本兜底。迁移盘至少容纳原数据、完整副本、包镜像和备份峰值。
5. 在新目录先检查校验和，再执行 `deploy.sh`、`ops.sh status`，核对实际镜像 ID、挂载及真实 SQL/业务数据。迁移复制的是数据，不能编辑校验清单中的脚本/编排；包内数据初始化文件变动时应另保存原始包校验结果并按迁移记录复核。
6. 通过业务核验后切换入口，并将新完整构建作为后续基线。失败时先停止新方案服务，按原映射回到旧目录和旧包；不要让两份数据库同时写同一目录。保留冷备和旧目录直到确认回退窗口结束。

新版同 ID 的实例只改服务名可直接增量升级。跨服务器移动、数据根/挂载目标变化、有状态镜像主版本或模板身份变化会被保守阻断；应先准备对应数据库的导出/转换/还原流程。删除持久化实例后，旧绑定目录保留在部署目录和升级冷备中；不要立即清理。重新新建实例会获得新 ID，不能自动接管旧目录。

无绑定目录的自定义实例，不备份容器可写层或镜像匿名卷。需要恢复的数据应先配置明确的持久化目录或单独进行业务备份。

## Compose 插件声明

本地 `docker-compose-linux-x86_64` 同目录需提供 `docker-compose-linux-x86_64.compose.json`：

```json
{
  "arch": "amd64",
  "version": "2.27.0",
  "source": "https://github.com/docker/compose/releases/download/v2.27.0/docker-compose-linux-x86_64",
  "sizeBytes": 12345678,
  "sha256": "填写实际64位SHA256"
}
```

`sizeBytes` 必须为文件真实字节数，示例数值不可直接使用；架构/版本来自对应发布记录。版本声明不能替代目标机执行 `docker compose version`。使用发布方校验和及可信取得渠道；本地自行计算的 SHA256 证明内容未变，不能证明来源可信。

导入检查完整 ELF 头、程序/节范围、可执行加载段、架构、长度和完整文件 SHA256，文件与元数据一同发布。旧库只有二进制、没有 meta 的插件会显示异常，重新下载或使用上述侧车重新导入；不要仅补一个未经核查的版本号。

## RPM/DEB 与静态 Docker

每个原生包独立附 `<文件名>.pkg.json`，例如：

```json
{
  "arch": "amd64",
  "kind": "deb",
  "dockerVersion": "27.5.1",
  "engineVersion": "27.5.1",
  "osFamily": "ubuntu",
  "osVersion": "24.04",
  "sha256": { "docker-ce_27.5.1_amd64.deb": "填写实际64位SHA256" },
  "components": { "docker-ce_27.5.1_amd64.deb": "engine" },
  "sources": { "docker-ce_27.5.1_amd64.deb": "填写取得该包的发布地址" }
}
```

- 必需角色为 `engine`、`cli`、`containerd`，其它包为 `dependency`。附件组 `dockerVersion` 填 `deps`，`engineVersion` 始终填其兼容的精确 Docker 引擎版本。
- 读取 DEB control 或 RPM header 的真实名称、版本、架构，比对角色和声明；Docker engine/cli 的上游版本必须匹配 engineVersion。支持 DEB gzip/xz/zstd/bzip2 的 control 归档。未知/损坏格式会拒绝。
- 原生包按 OS 家族/版本/架构精确选组，不能把另一发行版包标成当前 OS。工具无法仅凭包头确认全部 OS 依赖；需在同版本目标机验证安装及依赖闭包。
- 官方静态 Docker 可由应用下载，手工导入需对应架构；归档校验 gzip 完整性和全部必需二进制 ELF。静态包不代表所有内核/发行版都已认证。
- 只有 meta 声明且校验通过的文件会进入交付包，库内额外未声明文件阻断构建。`docker-offline/materials.json` 记录所交付文件、角色、来源、大小、SHA256 和实际原生包元信息。

## 工具自身存储迁移

设置中的普通“保存”仅改数据位置。“复制并切换”会等待保存及任务，冻结写入，把改变的根复制到新的空目录，逐文件校验后发布设置。旧根一直保留，失败不覆盖源目录；新目标不能与源重叠。默认镜像缓存下的 docker-pkgs 嵌套关系可保持，也可分别迁移。

迁移需要完整副本及约 128 MiB 事务余量，界面显示源/目标和估算；禁止符号链接/特殊文件，跳过任务锁及 staging 临时文件。遇到失败先查看全局任务记录，确认目标为空后重试。回退时等待任务及保存结束，在设置填回旧的五个有效根，普通保存并重新打开方案；回退不会把新位置期间的新增数据合回旧位置，应先另行备份。

## 超时、取消和故障恢复

全局任务最多同时 2 项，同类在途任务阻断重复提交。crane 查询/登录一般上限 60 秒、版本执行 10 秒、镜像拉取 1800 秒，下载使用其各自截止时间；存储锁等待上限 300 秒。取消会终止所属子进程树并清理临时材料，已发布的有效缓存不会因晚到取消被删除。关闭窗口前等待任务完成或取消后等待终止。

升级/恢复退出 2 表示自动回退未完成，必须保留控制台指定的快照及 `.before-restore.*`，检查真实业务状态后人工处理。单看日志“Running”或旧构建号不足以证明恢复成功。防火墙原生 nftables 不支持时明确失败；支持的 iptables 路径也应现场测试允许/拒绝来源，持久化和 Docker 重启只能在允许停机的维护窗口或隔离主机验收。
