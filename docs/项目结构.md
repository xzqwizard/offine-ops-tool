### 前端关键约定

- **自动保存**：组件里改数据一律 `store.commit(fn)`（立即持久化）或 `store.scheduleSave(fn)`（防抖），**绝不直接改 `store.project` 后不管**——那会导致内存与磁盘不一致且无 dirty 标记。
- **模板防空指针**：数据未就绪不用 `!` 非空断言渲染（v-loading 不阻止子树渲染），用三态 `v-if`（加载中/错误占位+重试/就绪）——SettingsView 曾因此白屏。
- **事件监听**：`listen()` 返回 promise，onUnmounted 时可能尚未 resolve；统一 `disposed` 标志 + resolve 后检查再注销（泄漏模式在多个组件出现过，抄现成写法）。
- **Tailwind + Element Plus 共存**：EP 变量映射到主题令牌（globals.css），布局类用 Tailwind，组件样式交给 EP。

### 后端关键约定

- **耗时命令必须 async + `spawn_blocking`**：Tauri 同步命令在主线程执行会冻结 UI（历史上连通性测试因此卡死），全部网络/下载/拉取/构建命令已改造，新增命令必须遵守。
- **命令参数**：Rust snake_case 自动映射前端 camelCase（`baseline_build_id` ↔ `baselineBuildId`）；`Option<T>` ↔ `null`。
- **删除/恢复类命令必须 canonicalize 后校验路径**（`Path::starts_with` 不规范化 `..`，直接比较可被穿越）——照抄 `delete_build` 的写法。
- **外网访问一律走 `net.rs`**：`http_get_with_settings`（自动代理）或 `crane_command`（注入环境变量），不要直接 `Command::new("curl")`。
- **写重要 JSON 用原子写**（tmp+rename，参考 `store.rs save_settings`）。

## 4. 数据流（两个核心链路）

### 构建链路

```text
前端 BuildPanel.handleBuild
  → 校验（validate.ts R 规则 + checkDockerPkgs R10 + 空间预检）
  → store.save()（先落盘，保证后端拿到最新方案）
  → invoke build_offline_package { project, autoPull, baselineBuildId? }
      builder::build_inner
        ├─ catalog::merged_catalog()      # ★ 前后端必须用同一目录层
        ├─ validate_render_fields()       # 注入安全门禁
        ├─ 每服务器 build_server():
        │    镜像三级解析（localImageTar → cache_file_for → pull_image_inner）
        │    升级模式：baseline_set 比对跳过未变更（键=引用@digest，对称）
        │    渲染 9 个模板（upgrade 模式 3 个）→ compose 过 serde_yaml 校验
        │    Docker 材料拷贝 → manifest.json → SHA256SUMS
        └─ 收尾：build-manifest.json / project-snapshot.json / SHA256SUMS.all
              / verify.bat / build-report.md / PORT-MATRIX.md(含部署顺序)
  ← BuildResult（事件 build-progress 全程推送）
```

### 镜像拉取链路

```text
pull_image(image, arch, registry?)
  → registry_login（私有仓库优先，stdin 密码，失败不阻断）
  → candidates（私有仓库 → 镜像源列表；仅 docker.io 引用回退）
  → 缓存命中？（键 = registry_repo-tag_os_arch.tar，含 tag/digest）
  → crane pull --platform linux/<arch> --format=tarball → <唯一临时名>.downloading
      └─ 进度监视线程：manifest 层总量 vs 临时文件增长 → image-pull-progress 事件
  → rewrite_docker_archive（RepoTags → 原始引用）→ 原子 rename 进缓存
  → meta.json（reference/platform/digest/source/pulledAt）
```

## 8. 工具链与构建（windows-gnu 专项）

本机工具链为 **WinLibs GCC 16.1（MinGW）**，三处特殊配置是历史踩坑的固化：

1. `Cargo.toml`：`crate-type = ["rlib"]`（cdylib → "export ordinal too large"）；
2. `.cargo/config.toml`：`RUSTC_BOOTSTRAP=1` + `-C linker-features=+lld`（GNU ld 2.47 产出有问题的二进制）+ rsproxy 源；
3. `build.rs`：
   - `WindowsAttributes::new_without_app_manifest()` + 全目标注入 windres 编译的 common-controls v6 清单（缺清单 → comctl32 绑 5.82 → 静默崩溃）；
   - WebView2Loader.dll 复制到 deps/examples（子目录 exe 找不到 DLL 会静默失败）；
   - `-specs=` 指向 mingw-specs-nodm.txt（lld 禁重复资源，需去掉 gcc 默认的 default-manifest 注入）——**换机器重新生成**：`x86_64-w64-mingw32-gcc -dumpspecs | sed 's/%{!shared:%:if-exists(default-manifest\.o%s)}/ /'`。

若 `cargo test` 报 STATUS_ENTRYPOINT_NOT_FOUND，按顺序检查：deps/ 与 examples/ 的 WebView2Loader.dll → 测试是否误放进 lib 内 → specs 文件是否存在。
