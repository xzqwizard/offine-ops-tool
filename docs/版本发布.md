# GitHub 自动版本发布

面向具有仓库写入权限的维护者，仓库地址：[xzqwizard/offine-ops-tool](https://github.com/xzqwizard/offine-ops-tool)。终端用户的下载和运行方式见 [README](../README.md)。

`.github/workflows/release.yml` 在推送 `v*` 标签时校验版本、执行前端测试和 Rust 格式/Clippy/测试、构建 Windows x64 MSVC 程序，再发布 GitHub Release。前端类型检查和生产构建由 Tauri 的 `beforeBuildCommand` 执行。只有构建和校验成功后才创建 Release 草稿；附件上传成功后公开发布。正式版本标记为 Latest，含 `-rc.1` 等后缀的版本标记为 Pre-release。

## 权限与试构建

工作流已随源码提供。仓库或 fork 需启用 GitHub Actions，并允许发布作业使用 `contents: write`；组织策略可能限制该权限。发布使用 GitHub 自动提供的 `GITHUB_TOKEN`，无需提交个人 PAT 或额外 Secrets。fork 的发布会写入其自身仓库；文档中的链接应按实际仓库地址调整。

可先进入 [Release 工作流](https://github.com/xzqwizard/offine-ops-tool/actions/workflows/release.yml)，点击 **Run workflow**，选择 `main`，标签留空。此时只运行测试和打包，产物保存在该次运行的 **Artifacts** 中，保留 14 天。正式发版前可用试构建核查安装包及便携包。

## 后续发版

以 `0.2.0` 为例，在仓库根目录执行：

```powershell
git switch main
git pull --ff-only origin main
pnpm release:version 0.2.0
pnpm release:check v0.2.0

git add package.json src-tauri/tauri.conf.json src-tauri/Cargo.toml src-tauri/Cargo.lock
git commit -m "chore(版本发布): 升级至 0.2.0"
git push origin main
git tag -a v0.2.0 -m "OfflinePreOpsTool 0.2.0"
git push origin v0.2.0
```

版本同步命令只更新四个文件中的应用版本，不刷新依赖。标签须与四个文件完全一致；不一致会在编译前报错。版本格式为 `X.Y.Z` 或 `X.Y.Z-rc.1`，各数字不超过 65535，不接受前导零或 `+build` 元数据。预发布示例：

```powershell
pnpm release:version 0.3.0-rc.1
pnpm release:check v0.3.0-rc.1
# 提交、推送四个版本文件后：
git tag -a v0.3.0-rc.1 -m "OfflinePreOpsTool 0.3.0-rc.1"
git push origin v0.3.0-rc.1
```

首个版本也可沿用当前 `0.1.0`，运行 `pnpm release:check v0.1.0`，确认配置已提交后推送 `v0.1.0` 标签即可。

在 [Actions](https://github.com/xzqwizard/offine-ops-tool/actions/workflows/release.yml) 查看构建进度；成功后到 [Releases](https://github.com/xzqwizard/offine-ops-tool/releases) 下载附件。

## Release 附件

| 附件 | 用途 |
|---|---|
| `OfflinePreOpsTool_0.2.0_windows-x64-setup.exe` | NSIS 安装包，内置 WebView2 离线安装程序，安装无需联网 |
| `OfflinePreOpsTool_0.2.0_windows-x64-portable.zip` | 便携主程序、使用说明和许可证；需已有 WebView2 Runtime |
| `SHA256SUMS.txt` | 安装包和 ZIP 的 SHA256 校验值 |

安装包支持简体中文和英语，跟随操作系统语言。内置 WebView2 会增加包大小；GitHub 构建机需联网下载该组件，用户安装时无需下载。程序的中间件目录和部署模板已编译到程序中；crane、Docker 安装材料和业务镜像仍需在应用中准备。便携版需完整解压到可写目录，默认配置和数据位于程序旁的 `data/`；在设置中覆盖存储根后，相关数据使用指定目录。

发布配置位于 `src-tauri/tauri.release.conf.json`，仅由发布构建显式加载。GitHub 的 Windows runner 使用 MSVC，并移除检出副本中的 GNU 链接与 Cargo 镜像配置，避免国内镜像影响云端构建；静态链接 CRT，减少便携程序的运行依赖。

当前未配置 Windows 代码签名，也未接入应用内自动更新。GitHub Release 发布完成后，用户下载安装新版本；升级前可通过设置备份应用数据。备份不会包含镜像、安装材料和业务数据，且密码需在恢复后重填；隐私边界见 [数据与隐私](数据与隐私.md)。

## 构建失败和重试

- 版本校验失败：修正四个版本文件，使用新的正确标签发版。
- 编译、测试或下载失败：查看失败步骤；临时网络故障可在该次运行中点击 **Re-run failed jobs**。
- 上传中断：Release 保留为草稿，重跑发布任务会补传附件，再公开发布。
- 在 **Run workflow** 中填写已存在的 `v0.2.0` 标签，可以重新构建并发布该标签；留空始终只构建。工作流会检出标签对应的代码。
- 已公开的同名 Release 不会被覆盖。修复应用或调整发布配置后，应提交新代码并发布新版本标签。旧标签对应的代码和工作流不会随 `main` 更新。

既有 `verify.yml` 仍会执行 Linux/Docker 场景验证。正式发版前应确认待发版提交的 Verify 工作流成功；Release 自身执行 Windows 打包所需的代码检查和测试。
